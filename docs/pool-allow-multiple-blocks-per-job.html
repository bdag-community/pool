Allow Unique Block Candidates Per Job

The pool previously treated a Stratum job as single-submit after the first block candidate. That is safe for preventing repeats, but it may be too restrictive for BlockDAG because distinct valid sibling blocks can share the same parent/template.

Old behavior Once jobData.blockSubmitted became true, every later block candidate for that job was rejected locally as duplicate_block, even if the block hash was different.
New behavior When POOL_ALLOW_MULTIPLE_BLOCK_CANDIDATES_PER_JOB=true, the pool accepts unique block hashes for the same job. Duplicate protection stays at the actual block-hash level, where it belongs.
Why it matters With multiple ASICs on one pool, several miners can work the same template concurrently. Suppressing all later candidates may lower accepted blocks per miner-hour.

Safety Boundaries

ProtectionStatus after change
Exact share replayStill blocked by per-job nonce/extranonce/ntime replay tracking.
Exact block duplicateStill blocked by global block-hash dedupe.
Health visibilityjobData.blockSubmitted still records that at least one block was submitted for a job.
Potential extra node loadOnly unique block hashes pass through, so extra load should correspond to potentially useful DAG blocks.

Feature Flag

SettingBehavior
POOL_ALLOW_MULTIPLE_BLOCK_CANDIDATES_PER_JOB=trueDefault. Allows multiple unique block hashes from one job, while exact block hashes are still suppressed globally.
POOL_ALLOW_MULTIPLE_BLOCK_CANDIDATES_PER_JOB=falseRestores legacy per-job single-submit suppression for controlled compatibility tests.
