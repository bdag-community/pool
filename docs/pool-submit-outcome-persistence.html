Pool Submit Outcome Persistence

Structured submit outcomes are useful only if they survive beyond logs. This branch records every solved-block submit attempt in PostgreSQL so dashboards, A/B comparisons, and incident reviews can use database truth instead of string-matching process logs.

Problem

Today the pool increments Prometheus counters and writes logs when a candidate block is accepted, stale, duplicate, or rejected. That is good for live charts, but it does not create a durable per-candidate history keyed by backend and template sequence.

Approach

Add an append-only block_submissions table and a storage helper. The submit path records a row after the node response is known. The row is independent of payout accounting, so rejected candidates cannot affect credits. A backend-labeled Prometheus counter is also emitted for live dashboards.

Review Boundary

This branch does not change whether miners are acknowledged, whether blocks are credited, or whether the configured node health state changes. It only persists facts already available in the submit path.

Data Captured

ColumnWhy It Matters
candidate_hashLocal solved candidate identifier, useful even when the node rejects the candidate.
node_block_hashNode-returned accepted block hash when structured submit v2 provides one.
backendShows which node accepted or rejected the candidate.
template_seqCorrelates submits with template freshness and WebSocket sequence data.
accepted, outcome, messageDurable source for accepted/rejected rates and incident reports.

Metric Added

pool_block_submit_backend_outcomes_total{node,outcome,reason} gives Grafana a low-cardinality live view of which backend produced each accepted or rejected candidate. Template sequence remains in the database table, not as a Prometheus label, to avoid high-cardinality time series.

Deployment Gate

Existing live databases need the migration before deploying a binary that calls Historical/superseded: this legacy RecordBlockSubmission path is not submission authority for POOL-DURABLE-SUBMISSION-JOURNAL/v1. Fresh installs retain the table through schema.sql for historical compatibility only; see the v1 journal. If insert fails at runtime, the pool logs the persistence failure but does not turn a node-accepted block into an ASIC reject.
